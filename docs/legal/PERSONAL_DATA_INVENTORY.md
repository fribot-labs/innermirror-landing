# 2. Current MVP Service Classification

InnerMirror MVP is classified as:

```text
Online Reflection
&
Project Continuity Service
```

The current MVP:

- does not continuously monitor users,
- does not perform automatic background analysis,
- does not send learner information to an external LLM for analysis.

Analysis begins only when explicitly requested by the learner.

---

# 3. Inventory Principles

This inventory follows the principles below.

## 3.1 Minimum Necessary Collection

InnerMirror should process only information reasonably necessary to provide the service.

Information must not be stored merely because it is technically available.

---

## 3.2 Identity Minimization

The current MVP does not require GitHub email as a permanent user identifier.

Preferred identity boundary:

```text
Supabase Auth User ID

+

GitHub Provider ID
```

---

## 3.3 No Hidden Identity Reconstruction

Different authenticated identities are treated as different InnerMirror users.

InnerMirror does not automatically infer identity equivalence using:

- email similarity,
- names,
- repositories,
- Reflection content,
- writing patterns,
- or behavioral similarity.

---

## 3.4 Source vs Derived Information

InnerMirror distinguishes:

```text
Human-Created Source Information

from

Service-Derived Information
```

Human-created information should receive stronger persistence protection.

Derived information should be stored only where necessary for service continuity.

---

# 4. Data Classification

Each data item is classified using the following statuses.

```text
PERSIST
=
Intended for long-term storage.

TEMPORARY
=
Processed temporarily but not intended for long-term storage.

RETRIEVABLE
=
Prefer retrieval from the original source rather than permanent duplication.

DERIVED
=
Generated by InnerMirror Runtime from source information.

DO NOT STORE
=
Not required for the current MVP.

OPEN
=
Final persistence decision has not yet been made.
```

# 22. Retention Rules

Active learner:

```text
Retain necessary records
for service continuity
```

Inactive learner:

```text
Delete after 3 years of inactivity
```

User-requested deletion:

```text
Delete entire InnerMirror user history
within the authenticated identity boundary
```

---

# 23. Identity Boundary for Deletion

Deletion operates by InnerMirror authenticated identity.

Conceptually:

```text
user_id

↓

All owned InnerMirror records

↓

Delete
```

Different authenticated identities are not automatically linked.

---

# 24. GitHub Independence

Deleting InnerMirror data does not delete:

- GitHub repositories
- commits
- pull requests
- branches
- GitHub account information stored independently by GitHub

The inventory covers only information controlled by InnerMirror.

---

# 25. Database Design Requirements

Future database schema must support:

- clear user ownership
- user_id relationships
- deletion by authenticated identity
- 3-year inactivity retention
- RLS-based user isolation
- source/derived data separation
- minimal GitHub duplication
- policy-version records

Database implementation must not precede these ownership requirements.

---

# 26. Production Security Gate

Before any PERSIST-class learner data is stored in production,
the following must be verified:

```text
□ Supabase production project

□ Production region

□ SSL / encrypted transport

□ RLS

□ User ownership policies

□ Service-role secret handling

□ Admin access controls

□ Backup behavior

□ Account deletion

□ Retention automation

□ Logging

□ International transfer review
```

# 27. Inventory Review Rule

This inventory must be updated whenever InnerMirror introduces:

- a new personal-information field,
- a new external service,
- a new AI/LLM provider,
- background synchronization,
- private GitHub repository access,
- new analytics,
- new identity linking,
- new retention behavior,
- or new persistence.

No new personal data category should enter production silently.
